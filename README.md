# 백엔드 스터디 카페

스터디원이 과제를 제출하고 댓글과 답글로 서로 피드백을 주고받는 웹 서비스의 백엔드 저장소입니다. 스터디장 1명이 프론트엔드를 맡고, 백엔드 스터디원 3명이 매주 같은 기능을 각자 구현합니다. 프론트엔드 담당자와 API를 맞추고, 직접 검증한 결과를 바탕으로 구현을 비교합니다.

## 구현 범위

| 영역 | 계획된 기능 |
| --- | --- |
| 회원 | 회원 정보 등록, 목록 조회·검색, 탈퇴 |
| 과제 | 과제 제출, 목록·상세 조회, 수정·삭제, 첨부 파일 업로드·다운로드 |
| 피드백 | 과제별 댓글 작성·조회·수정·삭제, 댓글 아래 한 단계 답글 |

초기 구현에서는 인증을 제외합니다. 테스트 회원 한 명을 작성자로 사용하고, 과제와 댓글의 작성·수정·삭제가 DB에 반영되는지 확인합니다.

## 스터디 진행 방식

1. **구현과 검증** — 세 명이 공통 요구 사항을 바탕으로 각자 코드를 작성하고, 정상 동작과 실패 사례를 직접 확인합니다. AI를 활용할 수 있으며, 사용한 코드의 동작과 설계 이유를 자기 말로 설명할 수 있어야 합니다.
2. **PR 제출** — 구현한 코드와 직접 확인한 결과를 모임 이틀 전까지 PR에 올립니다.
3. **상호 코드 리뷰** — 각 팀원은 다른 사람이 올린 백엔드 PR마다 코드 리뷰 댓글을 한 개 이상 남깁니다. 작성자는 받은 댓글에 답변합니다. 첫날은 질문, 둘째 날은 답변과 반영을 기본으로 하며 팀 일정에 따라 조정합니다. 스터디장의 프론트엔드 PR은 리뷰 참여가 선택입니다.
4. **발표와 병합** — 모임에서 각자 자기 PR의 구현 방식과 검증 결과를 설명합니다. 세 구현을 비교하고, 선정한 PR 하나에 합의한 수정을 반영한 뒤 `dev`에 병합합니다.

## 브랜치와 커밋

- `main`에는 시연·배포용으로 검증한 버전을 둡니다. `dev`는 기능을 모아서 확인하는 브랜치입니다.
- 스터디장이 매주 제시한 브랜치 이름 뒤에 `-깃허브아이디`를 붙입니다. 예를 들어 `feature/member-register`를 받은 `octocat`은 `feature/member-register-octocat`을 사용합니다.
- 기능 PR을 열 때는 `base`를 `dev`, `compare`를 자기 작업 브랜치로 선택합니다.
- 커밋은 `타입(범위): 제목` 형식으로 작성하며 범위는 생략할 수 있습니다. 예를 들어 `feat(member): 회원 등록 API 추가`, `docs: 회원 기능 명세서 추가`처럼 적습니다.

`dev`가 준비된 뒤 아래 명령으로 저장소를 받아 작업 브랜치를 만들 수 있습니다. 마지막 줄의 브랜치 이름은 예시입니다.

```bash
git clone --branch dev https://github.com/backend-study-winter/backend-study-cafe-be.git
cd backend-study-cafe-be
git switch -c feature/member-register-octocat
```
